# 项目愿景（Vision）

> 说明项目背景、定位、价值主张、生态边界、能力地图与阶段目标。已交付能力见 [requirements.md](./requirements.md)，待办排期见 [roadmap.md](./roadmap.md)，变更记账见 [changelog.md](./changelog.md)，工程设计约定见 [console-design.md](./console-design.md)。

## 一、背景与起点

1. 两周前从短剧创作切入，横向体验了 ComfyUI、剪映、即梦 AI、LibTV，以及剧本、大纲、脚本、分镜，均在皮毛层；体验额度用完未充值，期间没有成品产出。
2. 经 MotionGit 模板路线做出第一条拿得出手的成片，之后把配套本地工程整理成当前的 Web 控制台。
3. 本人技术背景：8 年前端（Vue、TypeScript、工程化），后端 Node 可用，Python 能写脚本；影视内容侧的剧本、分镜、节奏与素材审美仍在积累期。

## 二、项目定位

1. 第一服务对象：自己的本地出片流程，自用优先。
2. 架构原则：通用内核（.motion 读取、校验、类型定义、锁清单管理）与工作台界面分层；内核写成可抽离模块，成熟后再评估开源，不一开始就按通用第三方客户端设计。
3. 产品形态：兼容 `.motion` 格式的本地工作台；仅本机访问，不绑定官方站点，不代登录、不经手个人 key。
4. 明确不是什么：不是 ComfyUI 同类的节点编排引擎，不是自研渲染内核，也不是 MotionGit 官方客户端。
5. 前后端通过接口契约解耦：前端构建不写死后端地址，后端地址与 AI 提供商均可运行时配置；同一前端构建可连接任意兼容后端（本机、局域网或远程）。
6. 产品形态参照成熟 Web 面板的交互范式：仪表盘总览、依赖状态、配置页、日志区、密钥设置、目录视图；但定位是垂直创作工具的控制台，不做通用服务器运维功能（网站托管、数据库、系统进程、防火墙等）。
7. 创作动作不在面板内闭环：选题、写稿、素材落地、配音合成、渲染出片由用户在外部 AI 工具沟通并直接改磁盘文件；面板退为观测台，只做文件变动监测、素材与产物盘点、环境配置查看，以及标题、文稿、发布文案等纯文本轻编辑；重动作以预置提示词形式交外部 AI 执行。

### 2.1 可借鉴的成熟模式

1. 界面模式：仪表盘总览、依赖状态卡、配置页、日志与任务区、密钥设置、目录视图。
2. 信息架构：首页健康概览 → 资源管理（模板/作品/配音）→ 命令任务 → 设置。
3. 安全做法：密钥配置、白名单目录、操作留日志。
4. 只借鉴交互与信息组织，不照搬账号体系、服务器监控与运维功能。

## 三、价值主张

1. 自用效率：把模板、素材、配音、成片、环境状态收拢到本地一个界面，跑通从输入到出片的完整链路。
2. 技术沉淀：可复用的 reader、validator、TS 类型、锁清单管理等内核能力，未来可独立成包给其他工具复用。
3. 社区机会：`.motion` 属于早期新格式，工具层存在空白；用前端长板补这一层，自用流程和个人技术作品互相支撑，也可作为内容账号的工程类选题。

## 四、与相关生态的边界

### 4.1 与 ComfyUI 的异同

相似处：

1. 浏览器作为操作界面，重活放在本地后端和外部运行时。
2. 素材、模板、产物按本地目录组织，界面负责展示与操作。
3. 都是「模板/模型 → 填输入 → 出产物」的流水线思路。

差异处：

1. ComfyUI 核心是节点画布编排，拖节点、连边、定义数据流，工作流可保存复用；本项目目前是菜单、页面与表格，没有编排层。
2. ComfyUI 自行跑推理与采样；本项目渲染依赖模板自带 adapter 与 Chromium、ffmpeg，工具本身做调度与回显，不是渲染内核。
3. ComfyUI 有自定义节点与模型生态；本项目后端一期只有只读 GET 接口，执行队列尚未接入。
4. 长远可演进执行队列、参数表单与作品实例管理，不照搬节点画布的复杂度。

### 4.2 与 MotionGit 官方的关系

1. 兼容开放格式 `.motion`（当前本地模板 `specVersion` 为 `0.1.0-draft.1`）；实现上声明支持的版本与 runtime profile，未知版本和字段给出明确警告，不按前缀盲接受。
2. 不代登录、不代下载受门禁包、不经手个人 key；不破解 `protected-v1` 加密核心，不剥离凭据后宣称兼容分发契约。
3. 不宣称官方出品或官方背书；项目命名不含 MotionGit 品牌名。
4. 格式当前为候选草案、稳定版未冻结，兼容逻辑按版本隔离，不把草案假设写死。

### 4.3 与内容账号规划的区分

1. 工具项目（本文件）与内容账号规划是两条线；账号人设、栏目与发布顺序见 [content-plan.md](./content-plan.md)。
2. 交叉点：工具项目本身可作为「前端工程师搭 AI 工具链」的复盘选题，但文档与代码不混用两套口径。

## 五、能力地图

| 能力域 | 现状（一期） | 阶段目标 |
| --- | --- | --- |
| 环境检查 | 本地依赖版本、路径、就位状态探测；健康状态定时轮询 | 命令台依赖联动安装引导 |
| 模板浏览 | 元数据、许可、运行时、文件树与参数概要只读回显 | .motion 导入解压、凭据扫描、锁清单与哈希校验、参数 preset 预览 |
| 作品与素材 | 视频条目、配音、BGM、产物只读回显 | 发布配置写回、BGM 公共库、作品与条目菜单拆分、模板本地下载 |
| 媒体播放 | 波形初版、全局音视频单播 | 统一播放器、进度 seek、字幕波形对齐、版本画面对比 |
| 命令执行 | 白名单命令台：plan/prepare/preview/render/tts 异步排队、日志增量回流、取消；端到端出片链路待本机跑通 | 出片链路全流程跑通、产物回显；日志流式推送 |
| AI 助手 | 无 | 多厂商 BYOK 助手：用户填自己的 API Key，适配火山、Qwen、DeepSeek、OpenAI 兼容等提供商；文案、封面生成结果经后端写盘 |
| 工程化 | Vue3 + Vite + TS 基础工程 | 目录分层、接口与常量集中、运行时配置层、About 页架构拓扑与运行配置说明、Markdown 渲染、窄屏适配、组件拆包 |

## 六、阶段目标

1. 一期（已完成）：只读控制台骨架、环境检查、资源浏览、素材回显。
2. 二期近期（优先）：命令台执行闭环。白名单执行 prepare、preview、render、tts 等命令，日志回流，长任务异步轮询，模板依赖安装联动；先在本机跑通一条完整出片链路。
3. 二期中段：`.motion` 兼容层。本地 .motion 导入解压、凭据扫描、锁清单与 SHA256 校验、按 `params.schema.json` 生成参数只读视图。
4. 二期后段：素材与作品管理。发布配置写回、BGM 公共库与选用回写、作品/条目菜单拆分、模板本地下载、播放器重做。
5. 三期：AI 助手接入；评估内核抽离与独立发包；关注官方第三方客户端内测与 `creator/2` 契约，待条款明确再对接分发层。

## 七、红线

1. 面板是无状态纯客户端，后端地址运行时可配，可连接任意兼容后端；后端默认监听本机回环，跨机或远程访问需显式放开监听，并配套鉴权、CORS 白名单与写接口保护；未鉴权且带本地文件或执行能力的后端，不暴露到不可信网络。
2. 静态校验不触发付费生成；不代登录、不碰个人 key、不解密 protected 包。
3. 不宣称支持全部引擎，不宣称无依赖可跑；不把候选草案格式说成认证标准。
4. 公共仓只放确认可再分发的素材；私有角色人像、配音轨、选定 BGM、个人成片、字幕稿不入库。
5. 规范版本未冻结，涉及版本与 profile 的兼容判断保持隔离，不接受未知版本前缀的大包大揽。
6. 公网部署只放公开只读内容；个人工程、凭据、私有素材不离开本机，服务器不代理个人交付包、不存密钥。

## 八、命名原则

1. 产品名使用自有代号；副标题或描述写「兼容 .motion 的本地工作台」。
2. 不含 MotionGit 品牌名，不单独使用泛化的 motion；不使用官方 logo 与品牌圆环素材作为自有标识。
3. 当前 `package.json` 与 README 中的 ai-motion-studio 为临时名称，待代号确定后统一替换。
4. 若对外发布，README 与关于页需标注「非官方项目，与 MotionGit 无隶属或背书关系」。

## 九、工程结构（monorepo 已落位）

pnpm workspace 已纳入前后端与共享包：

```
apps/
  web/        # 前端控制台（Vue3 + Vite + TS + Naive UI）
  server/     # 后端服务（Fastify 5 + TypeScript，独立包）
packages/
  shared/     # 前后端共享的错误码、常量与契约类型；reader、validator 等内核能力后续抽离
studio/       # 业务资产目录，非 JS 包，不纳入 workspace
docs/         # 文档
```

1. `packages/shared` 承接可抽离内核，web 与 server 共同引用，类型与错误码保持单一来源。
2. Python 侧脚本（adapter.py、make_voice.py、uv 环境）不进 pnpm workspace，保留 PEP723 声明与目录约定。
3. 目录迁移作为独立重构提交，不与功能改动混合。

### 架构分层（About 页拓扑图依据）

1. 表现层：面板前端，Vue 静态构建，可本地运行或部署 Pages；无状态，后端地址与密钥运行时配置。
2. 接入层：HTTP API，访问密钥校验，CORS 白名单。
3. 服务层：Node 后端，负责环境探测、模板/视频/TTS/素材回显、命令台、AI 代理、配置管理。
4. 本地资产层：studio 下 templates、videos、tts、public、bin 等白名单目录。
5. 运行时依赖：Chromium、ffmpeg/ffprobe、uv/Python、node_modules。
6. 外部服务（可选，BYOK）：AI 厂商 API，使用用户本人 key。
7. 模板来源：本地 .motion 导入、GitHub 公开仓库、原站跳转下载。

## 十、对外展示与部署

1. GitHub Pages 演示站：纯静态托管，放项目介绍、界面截图与动图、特性清单、上手说明；只使用可再分发的 demo 素材。Pages 不运行后端，也不能直连本机回环服务。
2. 服务器后端形态当前不决策，留作远期评估，两种方案并列对比：
   - 公开只读 API：服务器只提供公开模板元数据、demo 预览与文档，不接个人 key、私有工程与成片；渲染仍留在本机。小 VPS 即可承担，安全边界清晰。
   - 远程完整工作台：把工程、素材、渲染放到服务器远程使用。需先补齐鉴权、加密、目录隔离与资源配额；Chromium 加 ffmpeg 的渲染负载不适合小机器，个人素材上公网的风险要单独设计。当前红线阶段不做。
3. 公网部分只暴露公开只读内容；个人交付包不在服务器代理解密或缓存。
4. 前端解耦设想：Pages 上的静态控制台可连接使用者自己部署的兼容后端。落地边界：后端需开放对应 CORS 并遵循同一套 API 契约；https 静态页调用 http 地址会触发浏览器混合内容拦截，需后端配合例外处理或用户本地运行前端；写接口处于后端所在环境的信任边界内，不做任意内网地址探测。
