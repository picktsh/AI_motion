# 服务器部署形态对比（评估稿）

> 结论先行：**不推荐远程完整工作台**。若要对外，优先“公开只读 API + 静态演示站”，且部署与个人工程彻底隔离。
> 本文只做方案对比与门槛清单，落地形态待拍板。

## 一、两种方案

### A. 公开只读 API
- 做法：单实例后端只读挂载脱敏样例目录（`studio/public`、公开模板缓存），暴露目录清单、任务状态样例与模板中心接口；不提供写接口、不执行命令。
- 资源：1 台 1C1G 云主机 + 反向代理 + 证书即可；也可用 Cloudflare Tunnel 临时演示。
- 风险面：只读接口 + 白名单目录；无 Key、无个人工程、无成片。
- 代价：接口需新增只读模式（禁写路由、禁命令台），样例数据要单独维护。

### B. 远程完整工作台
- 做法：把带写接口、可跑命令台的整套服务放公网，用户上传素材、跑渲染。
- 资源：渲染任务吃 CPU/内存与 ffmpeg，单机至少要 2C4G，还要对象存储与任务隔离。
- 风险面：任意文件写接口、命令执行、模板包上传（虽然已有静态校验与凭据扫描），一旦鉴权或路径隔离出问题就是远程代码执行级别的事故。
- 结论：个人项目不具备持续安全运维投入，**不做**。

## 二、门槛清单（任何公网形态都必须满足）

1. 鉴权：`ACCESS_KEYS` 必开，密钥轮换与最小长度要求写入部署文档。
2. 目录隔离：只挂载脱敏样例目录，不挂个人 `studio/projects`；写接口在只读模式下一律 403。
3. 命令台：只读模式下不注册任务提交路由，不暴露 `pnpm` 执行能力。
4. 数据：不上传个人 Key、成片、项目标题；日志脱敏（不含路径中的用户名）。
5. 传输：仅 HTTPS，限定 CORS 来源，关闭目录遍历类接口的模糊匹配。

## 三、建议

- 近期：不做公网部署，继续本机使用；对外只发 GitHub Pages 静态介绍（不连后端）。
- 中期若要展示真实交互：走方案 A，单开只读实例，样例目录独立，与个人工程机器物理分开。
- 触发条件：只有当“需要在别人的机器上看真实面板”成为硬需求时，才评估方案 A 的运维成本。
